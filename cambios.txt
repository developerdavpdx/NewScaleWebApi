 1. CONTEXTO GENERAL
------------------------------------------------------------------------
 - Proyecto: PTM NewScale (control de produccion, pesaje, scrap,
   inventarios y molinos de PTM).
 - Backend: ASP.NET Core Web API sobre .NET 9.
 - Frontend que la consume: PTM NewScale Web (ASP.NET MVC 5,
   .NET Framework 4.8, IIS Express en https://localhost:44390).
 - Repo del portal:
   C:\Paradox\DEVELOPMENT\NewScaleWebPlatForm
 - Datos:
     * SAP HANA Cloud (schema DBADMIN) para login, SKU/PT, historial
       de pesadas, tickets y consultas SAP.
     * SQL Server local (PtmNwScale2) para el modulo de Molinos,
       graficas, taras y algunas tablas de apoyo.
     * SAP Business One: Service Layer (REST) y DI API (COM).
 - La API expone Swagger en /swagger (se habilita en Development y
   tambien en Production; ver riesgos en la seccion 11).

 5. CONVENCIONES Y PATRONES
------------------------------------------------------------------------
 - Parametros: casi todo por [FromHeader]. Si el header no llega, el
   int.Parse/las conversiones lanzan excepcion y el endpoint responde
   500 con { "Message": "..." }. No hay validacion global.
 - Respuestas: NO hay un envoltorio unico. Conviven:
     { status = 200, data = ... }
     { status = 200, message = "..." }
     { response = "texto" }
     { TicketsInfos } / lista directa
   El portal a veces revisa "status", a veces "response", a veces el
   status HTTP. Al agregar endpoints conviene seguir el estilo del
   controlador vecino.
 - Errores: catch (Exception ex) -> StatusCode(500, new { ex.Message })
   o new { response = ... }. No hay middleware global de errores.
 - Codificacion: el codigo fuente tiene acentos rotos en varios
   mensajes (vienen de archivos guardados en ANSI). No se han
   normalizado.
 - Fechas: se usan DateTime.Parse/DateTime.Today en hora local del
   servidor. Los cortes de turno estan fijos en el codigo (04:30 y
   16:30) y en HorariosScrap para el modulo de scrap.
 - Auth: Login genera JWT, pero la validacion esta comentada en la
   mayoria de los endpoints y no hay [Authorize] global. Varios
   controladores aun reciben userId solo para auditoria.
 - CORS: politica "AllowAll" (AllowAnyOrigin/Method/Header).
 - Swagger: habilitado en Development y Production.
 - No hay pruebas automatizadas.

 6. BASES DE DATOS Y STORED PROCEDURES
------------------------------------------------------------------------
 HANA Cloud (Sap.Data.Hana, Sap.Data.Hana.Core.v2.1)
   - Connection string: ConnectionStrings:DefaulConnection.
   - Prefijo de SP: StoredProcedurePrefix ("DBADMIN" hoy).
   - SPs usados: SPPDX_LOGIN, SPPDX_GetSkuPT, SPPDX_GETEMAILS,
     SPPDX_GETEMAILSMOLINOS y los del modulo Sap/SapPtm.
   - Usan HanaConnection/HanaCommand/HanaDataReader directo.
   - Controladores: Account, Email, HistorialPesadas, Sap, SapPtm,
     PtmHana y partes de Corrugados/InfoTickets.

 SQL Server (PtmNwScale2)
   - Connection string: ConnectionStrings:SQLConnection.
   - EF Core 7.0.5 + repositorios en DAL. Tambien hay ADO directo
     (Microsoft.Data.SqlClient) en Molinos, Graficas, Taras,
     ProductTerminado y Scrap.
   - SPs propios: Sppdx_* (Molinos, ingresos, lineas).
   - DbSets: Lineas, EnvioSAP, EstadosSap, EnvioScraps, TicketsInfos,
     ScrapMolinos, HistorialPesadas, ProductoTerminados,
     AcumuladoEmbarques, BitHistorialPesadas,
     EstatusHistorialPesadas, BitacoraAsignacionLinias, UserTokens,
     SkuInfos, EstadosPesos, EstadosSemaforos, BaseImpresion.
   - Migraciones EF de 2023; los cambios recientes NO agregaron
     migraciones (fueron parametros de SP y cambios de codigo).

 OJO: el proyecto mezcla HANA y SQL Server en el mismo flujo. Por
 ejemplo, InfoTickets lee tickets de SQL Server, pero algunas
 validaciones van a HANA. Si una pantalla falla, primero identificar
 cual de las dos conexiones esta respondiendo.

 7. TICKETS, CORREOS Y TRABAJOS PROGRAMADOS
------------------------------------------------------------------------
 Plantillas y archivos (WebApiPtmHana/TicketPTM/):
   TicketPtM.html           -> ticket de PT (PVC/INY)
   TicketMolinos.html       -> ticket de molinos
   TicketScrap.html         -> ticket de scrap
   ReportEmail.html         -> reporte HTML de turno
   emailReporteTemplate.html
   LogoPTMHD.png, bell.png, check.png, fd.gif, datos.xlsx
   CorreJob.txt, CorreoEnvicado.txt, ErroresEnvioMail.txt,
   ErroresStore.txt, logEmai.txt
 - Las rutas son relativas a Directory.GetCurrentDirectory(), por eso
   la API debe arrancar con working directory WebApiPtmHana\.
 - El ticket se devuelve como HTML y el portal lo imprime / lo manda a
   labelary para la vista previa en imagen.

 Correos:
   - GetEmails / GetEmailsMolinos consultan SAP (HANA).
   - AddMailTxt / RemoveMailTxt / GetMailTxt usan archivos:
       C:\Paradox\ListaCorreos1.txt  (planta 1)
       C:\Paradox\ListaCorreos2.txt  (planta 2)
   - Si el archivo no existe, esas rutas responden 500. El portal lo
     maneja mostrando la lista vacia.

 Jobs (SheduleTurno1):
   - Se instancia manualmente en Program.cs (no es HostedService).
   - Timer 1: diario 17:45 -> cierre turno 1, envia reporte PPVC e INY.
   - Timer 2: diario 05:45 -> cierre turno 2, mismo envio.
   - Usa MailService.sendReport -> EmailServices.ObtenerDatosReporte
     (SP DatosReporte en SQL Server) y manda el HTML por SMTP.
   - SheduleTurno2 (BackgroundService) existe pero NO esta registrado
     en Program.cs; es codigo muerto.
   - OJO: si se levantan dos instancias de la API, los jobs se
     duplican (cada proceso crea sus propios timers).

 Logs:
   - Serilog escribe en C:\Paradox\PTM\Logs\log-YYYYMMDD.txt
     (ruta fija en Program.cs) y ademas loguea cada request.
   - Los jobs escriben sus propios .txt en TicketPTM\.

 12. COMPILAR, EJECUTAR Y PROBAR
------------------------------------------------------------------------
 COMPILAR
   - Abrir WebApiPtmHana.sln en Visual Studio y compilar (F6), o
     usar el MSBuild de VS en un Developer Command Prompt:
       msbuild WebApiPtmHana.sln /p:Configuration=Debug
   - No usar "dotnet build" (COMReference -> MSB4803).

 EJECUTAR
   - Normal: F5 en Visual Studio (perfil WebApiPtmHana).
     Levanta https://localhost:7227 y http://localhost:5079 y abre
     /swagger.
   - Por consola, desde WebApiPtmHana\:
       $env:ASPNETCORE_URLS="https://localhost:7227"
       .\bin\Debug\net9.0\WebApiPtmHana.exe
     Debe ejecutarse con working directory WebApiPtmHana\.
   - Verificar que 7227 este libre y NO usar 44390 para la API (esa
     la usa IIS Express del portal; una reserva huerfana deja el
     servicio http.sys en StopPending y obliga a reiniciar Windows,
     ver cambios.txt del portal, seccion 10).
   - Comprobar puertos:
       netstat -ano | findstr :7227
       netstat -ano | findstr :44390

 PROBAR (PowerShell)
   - Login:
       $body = '{"UserEmail":"...","Password":"..."}'
       Invoke-RestMethod -Method Post `
         -Uri "https://localhost:7227/api/Account/Login" `
         -ContentType "application/json" -Body $body
   - Scrap por planta (query, no header):
       Invoke-RestMethod "https://localhost:7227/api/Scrap/GetAllScrap?planta=1"
   - Tickets de Corrugado (headers):
       Invoke-RestMethod `
         -Uri "https://localhost:7227/api/InfoTickets/GetTickets2" `
         -Headers @{ numplanta = "1"; process = "Corrugado" }
   - Historial:
       Invoke-RestMethod `
         -Uri "https://localhost:7227/api/HistorialPesadas/GetAllHistorial" `
         -Headers @{ planta = "1" }
   - Swagger es la forma mas rapida de ver firmas y headers.
   - Si HTTPS falla por certificado de desarrollo:
       dotnet dev-certs https --trust

 ORDEN DE ARRANQUE PARA PROBAR EL PORTAL
   1) SQL Server y acceso a HANA Cloud disponibles.
   2) API en 7227 (F5 o exe).
   3) Portal en 44390 (F5 / IIS Express).
   4) Abrir la vista del portal y revisar Consola + Network.
